# GitHub Harness Agent implementation plan

Build a Python 3.12 GitHub App that takes a maintainer-selected issue through a verified pull request and subsequent review revisions. Python lets us call the upstream Harness2 recursion code directly and test both controller and executor with pytest. Use uv, FastAPI, SQLite in WAL mode on one controller host, and disposable Linux workers. Only the controller holds GitHub write credentials. A maintainer owns the merge.

## 1. Establish provider parity before wiring in GitHub

- [ ] Implement `providers.py` and a versioned provider manifest. On 2026-11-17 the incumbent web profile defined **Kilo, OpenRouter, NVIDIA NIM, Groq, Routeway and local Ollama**. Its reusable free-model catalog additionally defined **Google Gemini, Z.ai (Zhipu), Mistral and Hugging Face**. Preserve the six web route IDs (`kilo-free`, `openrouter-free`, `nvidia-free`, `groq-free`, `routeway-free`, `ollama-local`) and catalog aliases. Configured entries are evidence of intended support. Account eligibility, model availability and tool support require live validation.
- [ ] Build a whitelist-only profile importer for provider aliases, model IDs, capabilities, limits, default and ordered fallback choices. Keep credentials, private URLs and authentication headers in deployment configuration. Use an authenticated model gateway with provider-specific translation for Gemini and any incompatible tool-call formats. All Harness2 roles, including proposal and composition, use this routing layer.
- [ ] In `tests/test_providers.py` compare sanitized incumbent and imported manifests, including exact model and fallback order. Exercise tool calls, malformed responses, timeouts, unavailable models and 429 retry-after. Restrict fallback to allowlisted free routes, including eligible accounts for trial routes. On exhaustion, persist the retry time or pause. Record actual route, model, role and token usage. Require a live minimal exchange per enabled route and tool round trip per coding route before cutover. Report missing credentials or retired models explicitly.

## 2. Pick up eligible issues exactly once

- [ ] Implement `webhooks.py` and `store.py`. Verify GitHub App webhook signatures over raw bytes. Persist delivery ID and event in one transaction before returning success. Subscribe to issues, pull requests, submitted reviews and review comments. Use metadata read, issues read/write, contents read/write, and pull requests read/write. Scope installation to pilot repositories.
- [ ] On a maintainer applying `agent:ready`, fetch current issue state, repository policy and dependency status. Require an open, eligible issue and completed dependencies. Pin the base SHA and capture issue text, acceptance criteria and applicable repository instructions. Reconcile labeled issues periodically to recover missed events and unblock dependencies. Remove eligibility or close the issue to cancel pending work.
- [ ] Use a unique task per repository ID and issue number, with run generations, expiring worker leases and fencing tokens. Persist stage, base/head SHAs, branch, PR, review cursor, attempt count and external operation IDs. Recover expired leases on restart. Test duplicate labels under different delivery IDs, missed deliveries, concurrent claims, revoked installation and a late worker completing after lease expiry.

## 3. Run Harness2 on a repository task

- [ ] Implement `executor.py` with plain and Harness2 backends sharing one contract: task snapshot and immutable checkout in, patch, test evidence, route trace and usage out. Start from [upstream revision 6868817](https://github.com/google-research/harness2/tree/6868817518876de8fd170c6a8354daca273b6191). Use its demo and core recursion as the integration reference. Prove the adapter on a tiny fixture before adopting benchmark-specific runner code.
- [ ] For one sequential refinement step, propose harness edits, execute probes in separate clean workspaces at the same SHA, compose from observed traces, then execute the adopted harness to produce the patch. Record seed, model, instructions, harness version, candidate evidence and selected patch digest. Keep lessons scoped per repository. Require review before promoting a lesson into the shared baseline.
- [ ] Limit wall time, model requests, concurrent probes and patch size per task. Run commands and tests in disposable workers without host mounts, GitHub credentials or direct provider keys. Restrict egress to the gateway and approved dependency sources. Enforce limits outside the editable harness. Verify the patch in another clean checkout with trusted required checks. Test isolation, cancellation, empty patches, partial provider outages and a candidate that weakens tests to appear successful.

## 4. Publish one recoverable PR

- [ ] Implement `publish.py`. Check the task generation and eligibility, create a deterministic issue branch, publish the verified commit, then open a draft PR against the configured base. Include a closing issue reference, summary, checks and relevant limitations. Respect repo branch conventions. Mark ready for review after required checks pass.
- [ ] Persist intent before each GitHub write. After an ambiguous response, look up the branch SHA or PR by repository, head and base before retrying. Update the existing PR. Use an expected-head check on pushes and abandon stale patches when someone else pushes. In a disposable GitHub repo, kill the controller after branch creation, push and PR creation in separate runs. Each restart must end with exactly one branch and PR and preserve human commits.

## 5. Turn review feedback into verified commits

- [ ] Implement `reviews.py`. On a submitted review from an authorized reviewer, fetch its body and all pages of current unresolved threads. Process actionable comments in a submitted COMMENTED or CHANGES_REQUESTED review. Include standalone follow-up comments on known threads after a short debounce. Ignore self-events, resolved threads and approvals without requests. Persist comment IDs and revisions so redelivery and edits are distinguishable.
- [ ] Batch feedback against one PR head. Map outdated comments to current code before changing it. Ask in-thread when requirements conflict or intent is ambiguous. For actionable feedback run the same isolated edit and verification path, push to the same branch and reply with commit and check evidence per thread. Leave resolution to the reviewer. Pause after three automated repair rounds or repeated no-progress output.
- [ ] In `tests/test_reviews.py` cover a review containing only body text, multiple inline threads, two reviews arriving during one run, an edited comment, a human push, PR closure, bot loops, and a crash after push before replies. A retry must recover missing replies without duplicating commits.

## 6. Qualify the replacement and rehearse rollback

1. **Offline CI.** Run `uv run pytest` with signed webhook fixtures, a fake GitHub API, deterministic model responses and real Git repositories. Exercise the full issue → PR → request changes → revised commit sequence, including each recovery case above.
2. **Matched replay.** Select at least 20 closed issues across bug fixes, features and review-heavy changes. Freeze original issue text, base SHA and hidden acceptance checks. Keep eventual patches, later discussions and held-out tests outside worker reach. Run the incumbent, plain Python controller and Harness2 controller on the same inputs with matched providers and budgets. Blind-review outputs. Compare accepted patches per issue, human correction minutes, review rounds, latency, provider quota use and failures. Record fallback differences.
3. **Shadow and canary.** Shadow ten live issues with publishing disabled. Then assign ten labeled issues exclusively to the new App, leaving the incumbent responsible for other issues. Include a real review repair, controller restart, quota exhaustion and rollback drill. Extend the trial when review or provider coverage is missing.
4. **Proposed release gates.** Every enabled incumbent route passes its live smoke test. Every catalog adapter passes its contract tests. Require zero duplicate PRs, lost human commits, unauthorized writes or paid fallbacks. On matched replay require at least as many accepted patches as the incumbent and no increase in median human correction time. Publish per-issue results and paired differences. Treat small or inconclusive samples as grounds to extend the pilot. Enable Harness2 by default only if it improves acceptance or reduces reviewer time within the agreed quota and latency budget.
5. **Transfer ownership per repository.** Disable incumbent intake for the selected label before enabling new intake. Finish existing PRs with their original owner. To roll back, pause new leases and publishing, invalidate active worker generations, reconcile outstanding branches and PRs, then restore incumbent intake. Assign each open task a single owner before resuming. Require maintainer sign-off on the evidence and rollback drill.
